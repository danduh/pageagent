## Phase 0 spike findings applied (2026-07-23)

> **Update — Canary re-test (Chrome 152, 2026-07-23; see `spikes/FINDINGS.md` → *Canary run*).** The native-tool-calling assumption is now **RE-TESTED and CONFIRMED** (no longer merely flagged): on Chrome 152 `create({ tools })` is accepted but the model **never dispatches** (it emitted `run_jobs(...)` as text and hallucinated tool names) → the **manual capped `INTENT_SCHEMA` loop stays**, decision rule not met. `create()` + `prompt()` + `responseConstraint` structured output all work in a page context **without a gesture** (Nano `available`), so the Prompt-API-host *viability* risk is largely retired — only the exact MV3 side-panel-document / extension-origin confirmation remains (Phase 1). `document.modelContext` is **present** on 152 (absent on 148). Structured output was valid JSON but **not strictly schema-faithful**, so the parse/coerce layer is validated as necessary.

Both derisking spikes ran (see `spikes/FINDINGS.md`). Environment: embedded Chrome 148 / Electron — a **strong directional signal, not the final side-panel verdict**. Resulting refinements:

- **`Element-handle strategy` → RESOLVED (Spike B).** `WeakRef` goes stale; DOM index breaks under reorder; only a stable `id` and the accessible-name/text survived on their own merits. Adopt a **multi-signal fingerprint** `{role + accessible-name + type + nearby-text/group-ordinal + stable-id-if-present + WeakRef}` — primary = role+accessible-name re-query, WeakRef = liveness-negative only, positional never acts, id confirmatory — with a mandatory match-verification gate. Step-level refinements: **3.0** types re-resolution as a four-outcome union `resolved-verified | not-found | ambiguous | stale` (not a boolean); **8.2** keys staleness on fingerprint mismatch (not node existence); **8.4** re-checks role+name+type+visible+enabled against the stored fingerprint; **8.5** DECLINES on not-found/ambiguous/stale (ambiguity is a first-class decline); **D2** spoken anchor = role+accessible-name+nearby-text/ordinal with a spoken decline on ambiguity; **D11** = decline-on-ambiguity.
- **`Prompt-API host document` → RESOLVED: the side panel (Spike A2, 2026-07-25 — supersedes the "still OPEN" note below).** `LanguageModel.create()` **succeeds in the real MV3 side-panel document** at the extension origin on Chrome 152 (`availability: "available"`); the brain lives in the side panel, **no offscreen document**. See `spikes/FINDINGS.md` → *Spike A2*. _(Original 148 note, retained for history:)_ Chrome 148 exposes `LanguageModel` as a function with `availability() === "downloadable"`, but `create()` is **user-gesture-gated** and did not run, and the context wasn't the real side panel. **Step 1.5** makes model-download an acceptance criterion: split passive `availability()` detect from a user-gesture `create({ monitor })` provision (no preceding `await` — an await can consume the activation); **Step 7.1** renders `downloadable` as an *actionable* state, distinct from `downloading`/`unavailable`.
- **Native tool-calling (Step 9.2 / docs/07 §2 / Risk 5) → FLAGGED FOR RE-TEST, not flipped.** Tool-calling was **not** exercised (`create()` never ran); the capability page's "Stable" is unverified. The manual capped `INTENT_SCHEMA` loop stays committed until a live bake-off (decision rule fixed in advance: flip only if materially more reliable **and** stable across ≥2 Chrome versions; any change scoped to the model-output→intent parse seam only). Structured JSON output ≠ tool-calling and is tested independently.
- **One definitive follow-up** (needs the real extension side panel on the user's Chrome + Claude-in-Chrome connected): fire `create()` from a click handler; run the native-tool-calling vs. `INTENT_SCHEMA` bake-off + an independent structured-output test; record download UX. Tracked on #5. Spike B edge cases (decline-on-ambiguity vs real data, shadow/virtualized/canvas/cross-route, real-framework id stability, re-query cost) tracked on #6.

## Scope & how to read this plan

Two scope options, delivered as **one continuous roadmap** — Scope A comes first and Scope B continues from it, so the owner chooses how far to go without re-planning:

- **Scope A — Design-first UI slice (Phases 0–6):** a loadable, clickable, accessible MV3 **side panel** faithful to `PageAgent.dc.html`/`DESIGN-BRIEF.md`, driven entirely by **realistic mock data behind a narrow stubbed-engine interface**. Fast path to a demoable, WCAG-conformant product shell. Nothing here depends on Gemini Nano, WebMCP, or embeddings.
- **Scope B — Full product (Phases 7–11):** replaces the stub with the real engine (capability detect → DOM scan → tool-gen → WebMCP/fusion → on-device capped intent-loop → execute → safety gating → observed report-back), honestly sequenced against capability reality, plus clearly-marked Later work.

**Phase tags:** `[SCAFFOLD]` build/tooling infra · `[UI]` · `[SAFETY]` · `[A11Y]` · `[ENGINE]` · `[QA]`. Phases 0–1 are `[SCAFFOLD]`; Phases 2–6 are the Scope A **UI** milestone (with `[SAFETY]`/`[A11Y]`/`[QA]` folded in as first-class); Phases 7–11 are the Scope B **ENGINE** milestone.

**Every step is a thin vertical slice** — a self-contained deliverable that is demoable/verifiable on its own, with acceptance criteria. Steps are numbered within phases (Step 1.1, 1.2…). Each phase ends with a **Demo / verification** line.

**Real vs. mocked at each milestone (stated honestly up front):**
- Phases 0–6: engine is **stubbed** — mock `Page`s, mock tool-sets (sparse + dense 50–100), forced capability states, scripted transcripts; **no live DOM execution**. Report-backs, gates, and locus states are all driven from fixtures.
- Phases 7–8: **real** scan / tool-gen / fusion / execute, but not yet model-driven (manual `Run`, Tier-0 executes directly).
- **Phase 9 = First Functional Milestone:** one **real, confirmed action end-to-end on a live page, on-device**, with a truthful Confirm-gate and observed-result report-back. Deferred/stubbed here: robust multi-step re-scan (Phase 10), cloud fallback (Phase 10), embeddings top-k (Phase 11, keyword fallback only), voice/profiles (Phase 11).
- Capability reality is honored throughout: **native tool-calling is unusable → a manual capped JSON intent-loop only**; Nano is weak at long planning → **single-action reliability is the core**; WebMCP/embeddings are origin-trial/Canary → **detected and gracefully degraded, never hard-required**.

- **Deliverable:** extend the loop to sequence steps — observe → **re-scan → re-plan** between actions, refusing tools that no longer map to the live page (via the freshness liveness check), honoring Stop/Escape at any point, and handing back at the cap with the honest "single confirmed action is the reliable core, not an unattended chain" framing (REQ-AGENT-3/4/5/6). **Multi-step is explicitly best-effort, not guaranteed.**
- **Acceptance:** a 2-step request ("filter to failed jobs, then rerun them") re-scans between steps and acts on the refreshed tool-set; Stop/Escape halts mid-loop immediately and leaves the page in a known state; if the page changes such that a planned tool no longer maps, the loop **stops and reports rather than firing a stale tool**; reaching the step cap produces the honest hand-back framing, not a silent stall.

**Step 10.2 — Graceful degradation wiring (no-model / no-embeddings)** · Size **M** · Depends on: 8.1, 8.4, 9.2
- **Deliverable:** architectural separation so the mechanical surfaces work with **zero model** — browse Tools, run one via Execute, inspect Scan/Gen stay fully usable when the model is absent and cloud isn't opted in; **Chat is disabled-with-explanation, not broken** (REQ-REL-2). Provides a simple **keyword/substring tool-matching fallback** for retrieval when embeddings are unavailable, and an honest "narrow your request" path on large tool-sets (REQ-RETR-4).
- **Acceptance:** a model-off build still lets the user browse, run, and inspect tools end-to-end; Chat shows an honest disabled state naming what's unavailable and what still works — never a dead panel; with embeddings absent, keyword matching returns a usable candidate set on a small page; on a dense tool-set with no retrieval, the user is asked to narrow rather than fed 100 tools blindly.

**Step 10.3 — Cloud fallback path (opt-in, labeled, Offshore)** · Size **M** · Depends on: 9.2, 5.7
- **Deliverable:** a clearly-labeled bridge used **only** when on-device is unavailable **and** the user explicitly opts in **per use** — sends the tool-list + request to a configured cloud endpoint to produce the same `INTENT_SCHEMA` decision, then executes locally through the **same** safety/execute/report pipeline. Drives the Off-device locus + per-turn cloud label; never engages silently; disclosure shown **before** first use (REQ-AVAIL-2, REQ-PRIV-3). **Ships disabled-by-default; must not dilute the on-device thesis.**
- **Acceptance:** with Nano forced unavailable, the loop is disabled until the user picks "Use cloud once" — **nothing leaves the device before that explicit act**; a cloud turn flips the locus to Off-device and tags the transcript turn with a per-turn cloud label; the cloud decision runs through the identical confirm-gate + execute + report pipeline; the disclosure states what is sent and warns against sensitive pages, shown before the send. (Endpoint/provider + whether it ships in MVP = owner decision.)

**Step 10.4 — Fixture page suite + engine test harness** · Size **M** · Depends on: 7.4, 8.3, 9.1, 9.2

- **Acceptance:** every fixture is reproducible locally and covers one named reliability risk (SPA, shadow DOM, icon-only, dense, declared-tools, high-stakes); automated tests assert scan coverage, honest-unlabeled output, tier assignment, and certainty-ladder mapping; loop-parser tests feed malformed/fenced/string-args output and assert clean extraction; the run is green in CI with each honesty edge exercised.

**Step 10.5 — Scope-B accessibility re-verification against real engine output** · Size **M** · Depends on: 9.2, 10.1, 6.3

## Risks & mitigations

1. **Design-file access is auth-gated** (`PageAgent.dc.html`). *Mitigation:* build from `DESIGN-BRIEF.md` §10 now with all values marked provisional; confine raw hexes to the primitive token layer (Step 2.1) so true-up rework is one file per category; only Step 6.5 (pixel-final fidelity) is blocked — the whole shell is buildable and demoable without the file.
2. **The "monorepo root" is not a materialized Nx workspace** (no `nx.json`/`nx`; dangling `../node_modules/nx`). *Mitigation:* Steps 0.1–0.3 are designed to demo with **no build**; Step 0.4 resolves the wiring (standalone project vs. materialized root) before any build target runs.
3. **Prompt API in an extension needs an origin-trial token + model download + capable hardware.** *Mitigation:* Step 1.5 env-injects the token (never committed), Step 7.1 probes honestly, and the header locus + banner degrade to truthful "unavailable" everywhere; cloud fallback (10.3) is the labeled opt-in escape.
4. **DOM→tools reliability across the messy web** (SPA re-render, shadow/virtualized/canvas, icon-only). *Mitigation:* honest coverage summary (7.3), honest-unlabeled tool-gen (7.4), pre-execute liveness re-check + locate-or-decline (8.4/8.5), and the fixture suite (10.4) — **never present an unreliable action as reliable** (REQ-REL-3).
5. **Native tool-calling is unusable; Nano is weak at planning.** *Mitigation:* the brain is a manual capped `INTENT_SCHEMA` loop (9.2) optimizing **single-action reliability first**; multi-step (10.1) is explicitly best-effort and bounded; embeddings top-k (11.1) is Later with a keyword fallback.
6. **Auto-execution in authenticated sessions + over-trust / confirm-gate reflex.** *Mitigation:* the reversibility ladder leans on a confidence bar + deterministic heuristics + conservative high-stakes bias (8.3), the one-tap reverse is the visible net (9.1), friction is spent as scarce currency (Tier-0 shows no modal), and the Tier-2 hard-stop floor is un-configurable.
7. **MV3 strict CSP forbids eval/remote code** → standard Vite HMR won't run in the panel; multi-entry (panel/SW/content/MAIN-world) output must stay eval-free. *Mitigation:* Step 1.2 lands watch-rebuild + reload as the reliable path (CRXJS only if CSP-clean); Step 1.1 verifies zero CSP violations.
8. **Narrow ~320–400px column vs. dense Tools + truthful gate previews + 7:1/44px at 200% zoom** (open decision D1). *Mitigation:* Step 5.4 pressure-tests it and **flags rather than shrinks below the floor**; if it can't carry the load, that's the trigger to revisit the form factor.
9. **Forced-colors erases custom color** (Windows High Contrast). *Mitigation:* meaning is always re-expressed via icon + text + border/material (Steps 2.10/2.11/4.x); a forced-colors specimen is captured (2.11) and the gate is verified legible there (4.3).
10. **Automated a11y (axe) catches a fraction of issues.** *Mitigation:* the flagship claim rests on the **manual AT test plan** (6.3) — treated as an acceptance gate, not polish.
11. **Cloud fallback contradicts the thesis if misused.** *Mitigation:* disabled-by-default, opt-in-per-use, labeled, Offshore-material, per-turn cloud label; runs the same safety pipeline (10.3).
12. **WebMCP is a moving W3C draft.** *Mitigation:* isolate all of it behind the `modelContext` adapter (8.1) with an internal registry as the reliable base, so a spec change touches one module.
13. **Prompt injection.** *Mitigation:* protection is **structural** (page content only ever inert data/observations; every action user-provenance-tagged and refused otherwise; 9.2/4.6) — **never** framed as detection.
